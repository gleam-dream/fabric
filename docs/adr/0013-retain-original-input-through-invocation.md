# Retain original input through the existing invocation service

<a id="adr-0013"></a>

- On 8 October 2026 the owner accepted history-aware agent invocation as a generic Fabric capability. Applications retain conversation data and domain rules; Fabric retains execution input and its durable boundary. A separate conversation resource would add lifecycle ownership that this requirement does not need.
- Source inspection at `c92e97ca3357c15dd26a2fcb59a77bedcffda539` found that keyed agent invocation compared the first transcript user message, whereas graph invocation delegated original-input comparison to its runtime. Imported history invalidates the first-message assumption, so agent comparison belongs at the core boundary and includes the complete original input.
- Persisting the initial boundary also separates generated messages and current answer attempts from historical context. Agent record version 8 carries that distinction; retaining old reads and refusing unrepresentable old writes preserves the existing compatibility policy. Correlation and live credentials identify observations or authority rather than execution input.
- Expanding the accepted record envelope increments retention, discovery and statistics projection versions. An older reader may already have indexed v8 bytes as unknown; refreshing those projections under the new reader must revisit them without rewriting execution bytes.
- Existing transactional delivery covers application acceptance before Fabric admission. Retained outcomes and an idempotent application transaction cover completion before incorporation. Pool sharing cannot prove atomic admission, so this decision adds no adapter admission transaction, competing queue or application recovery scanner.
- An application graph may make incorporation a retained operation when its interruption and idempotency contract is explicit. It still needs an admission bridge and cannot turn a possibly committed application effect into a safe unconditional retry. The generic invocation capability does not depend on selecting this alternative.
- Prior disposable history experiments informed the requirement but are not adopted evidence for this implementation. Compatibility, external consumer and PostgreSQL scenarios must establish the delivered behavior independently; deterministic provider fixtures do not establish live-provider acceptance.
